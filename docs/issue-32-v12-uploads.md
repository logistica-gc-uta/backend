# Issue 32: ADMIN image proxy and gallery (implementation awaiting verification)

## Contract and boundaries

Only JWT ADMIN can call these `/api/v1/admin/catalog` mutations. `POST /uploads` accepts multipart `file` and returns 201 `{uploadId,secureUrl,publicId,format,bytes,width,height,status:"UPLOADED"}`. `POST /products/:id/images` accepts exactly `{uploadId,altText,isPrimary,position}` and returns 201 `ProductImage`. `PATCH /products/:id/images/:imageId` accepts a nonempty subset of `{altText,isPrimary,position}` and returns 200. `DELETE /products/:id/images/:imageId` returns 204 with no body. No browser-signed request, arbitrary URL/publicId association, base64 input or API secrets in responses. Controller-scoped filter returns `{error:{code,message,details,requestId}}` for guard and service errors; original endpoints are unchanged.

Maximum file size 5 MiB (5,242,880 bytes), JPEG/PNG/WebP only, MIME must agree with decoded content, width/height 1..8192. Sharp fully decodes before any provider work; empty, forged, truncated, oversized or unsupported files fail without creating a reservation. Gallery slots are integer positions 0..5; at most six, unique positions and one primary. Position changes swap occupied slots atomically by removing and reinserting the affected image rows with identical IDs and upload references inside a product-row lock. Selecting a different primary demotes the previous primary in the same transaction. Only the original actor can attach an unexpired, unused `UPLOADED` UUID, checked under product-then-upload locks using the PostgreSQL clock. Once attached, an asset is never attachable again. Product `updatedAt` is set from the DB clock. No product/category/order price or publication is modified by image endpoints.

**Approved S7 published-primary rule (implementation NOT VERIFIED):** deleting or demoting the sole primary on a published product returns 422 `IMAGE_ASSOCIATION_FAILED`, without automatic unpublication or any change to images, positions, metadata, asset status or `updatedAt` (including combined PATCH fields). Promoting a different valid attached image demotes the old primary atomically in the same transaction; the old nonprimary can then be deleted. A draft can lose its primary without publishing or changing unrelated images. Product-row locks serialize these operations with publication and category edits; invalid requests fail before writes and PostgreSQL rolls back any transaction error.

## Provider provenance and failure recovery

A random server-owned public ID under `regalia/products/` and an actor-scoped `UPLOADING` reservation with local metadata and 24-hour expiry are committed **before** any HTTPS request. Reservation failure does not call Cloudinary. The injected `UPLOAD_PROVIDER` adapter is implemented with Cloudinary's signed HTTPS Upload API; the backend alone reads `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`. Cloudinary `public_id` must equal the reserved ID; response must have matching decoded format, bytes and dimensions and a trusted HTTPS `res.cloudinary.com/<cloud>/image/upload/.../regalia/products/<id>.<ext>` URL. A successful upload transitions to `UPLOADED` and responds only after DB commit. Provider uncertainty, mismatch, or DB acknowledgement failure gives 502 `UPLOAD_FAILED`; the durable `UPLOADING` row remains keyed by publicId for cleanup/reconciliation, not just a log line. Missing configuration fails with sanitized 502 and no remote call.

Unlink commits image removal plus asset `CLEANUP_PENDING`; no provider deletion occurs in the HTTP transaction. Optional bounded cleanup (`CATALOG_UPLOAD_CLEANUP_ENABLED=true`, disabled in tests) claims up to ten due assets per minute. Expired `UPLOADING`/`UPLOADED` and due `CLEANUP_PENDING` rows are claimed on their own row with `FOR UPDATE SKIP LOCKED`, incremented attempts and a five-minute `cleanupAt` lease committed before calling provider. An attached image blocks cleanup; pending/claimed uploads cannot attach. Only acknowledged `ok` or `not found` yields `DELETED`. Uncertain deletion keeps pending status with retry timestamp/error. No network operation holds DB locks. The future purchase snapshot model (#33/#34) does not yet exist: BEFORE connecting it, extend the cleanup guard to check persistent historical image references and retention policy; do not assume a nonexistent receipt table. **Provider deletion cannot be considered safe for historical snapshots until that integration is designed.**

## HTTP errors and verification

400 `VALIDATION_ERROR` for invalid/unknown/null JSON fields; 401 `UNAUTHENTICATED`; 403 `FORBIDDEN`; 404 `PRODUCT_NOT_FOUND` for missing product/image; 413 `IMAGE_TOO_LARGE`; 415 `IMAGE_UNSUPPORTED`; 422 `IMAGE_ASSOCIATION_FAILED` for foreign/expired/reused/conflicting image associations; 502 `UPLOAD_FAILED` for missing provider configuration/failed or unverified provider acknowledgement. Unexpected reservation failures are sanitized 500 `INTERNAL_ERROR`. No provider or DB diagnostics appear in HTTP details. 404 `PRODUCT_NOT_FOUND` for an image missing under a product uses the existing stable catalog code; no invented image-not-found code.
