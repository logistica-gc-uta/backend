`public.productImage` (`ProductImage`/`prisma.productImage`): id, productId FK, uploadId unique FK, publicId, secureUrl, altText, position int4 0..5, isPrimary boolean. Unique `(productId,position)`, partial unique `(productId) WHERE isPrimary=true` enforce at most one primary; six possible occupied slots bound gallery to six. Reorders MUST hold `lockInventoryProduct` on product first, then lock relevant images, perform a single transaction using nonconflicting intermediate positions only if necessary (constraints are immediate; preferred delete/insert or temporary position is forbidden by range; a single SQL CASE update can also conflict). No network request while holding DB locks. Publication and category deactivation use ONE lock order: lock category row first, then affected product rows in sorted ID order, then image rows if needed. Category deactivation locks the category first and revalidates affected products; do not reverse category/product order anywhere. Other product mutations (absolute stock, prices and gallery) lock product first when they do not also acquire a category lock. Gallery attach locks product THEN uploadedAsset; no path may lock upload then product. `public.uploadedAsset` (`UploadedAsset`/`prisma.uploadedAsset`): id, actorId FK to User, server-generated publicId unique, **nullable** secureUrl, format jpg/png/webp, bytes 1..5242880, width/height 1..8192 (validated local file metadata), status **UPLOADING by default**|UPLOADED|ATTACHED|CLEANUP_PENDING|DELETED, expiresAt, createdAt, attachedAt nullable, cleanupAt nullable, cleanupAttempts default 0, lastCleanupError nullable. On provider success, persist returned secureUrl and confirmed metadata, transition to UPLOADED, and return 201 only after that commit. Failure/uncertain provider outcome leaves a durable row keyed by publicId for audited reconciliation/deferred cleanup; do not rely on logs to preserve the orphan. Expired UPLOADING and UPLOADED rows must atomically transition to CLEANUP_PENDING (upload-row-only claim committed before network deletion). Lock product THEN upload row within the same transaction; create image and mark ATTACHED/attachedAt atomically. ## Money limits and migration

SQL storage is PostgreSQL signed int8 (up to 9223372036854775807), but **this seam constrains persisted Product.priceCents to 1..9007199254740991**, so Shop JSON can be a safe integer. This is a representability boundary, NOT a business pricing ceiling: at the top end Float dual-write cannot roundtrip every cent, so the shared helper also rejects any such value; change of the legacy representation requires a new version, not rounding. Legacy order total can be zero and receives nullable cents; `OrderItem.price` and `Product.price` require positive cents to backfill. Malformed/nonfinite/negative, >2-decimal and overflow values remain NULL for manual audit; Shop never exposes them. Numeric source for SQL backfill is `float8::text::numeric` with regex guard, not `round(float8 * 100)`. PostgreSQL Float text uses its shortest round-trip decimal spelling; this is the explicit historical interpretation (not a claim that IEEE binary is decimal exact). A Float accumulated total such as 0.1+0.2 may remain NULL: do not infer its value from mutable/current products. Products with invalid legacy amounts cannot be newly ordered by the dual-write route until an operator resolves the original data; existing orders and original Float bytes remain.
